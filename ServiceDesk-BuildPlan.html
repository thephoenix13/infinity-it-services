ServiceDesk
Build Completion Plan

Phased implementation roadmap for all missing features — from critical inspection gates to branch reporting, customer portal, and push notifications.

⚠️
Covers 6 phases over ~8 weeks. Phase 1 (Inspection & Estimation) is the critical path — without it the core job lifecycle is incomplete: staff can currently move jobs to In Service without any customer approval. All subsequent phases layer on reporting, portal interactivity, branch configuration, and external integrations.
Phase 1 · Critical Path

Inspection & Estimation

The estimate → approval → work gate is entirely missing. Staff can currently transition any job to "In Service" without the customer ever seeing or approving an estimate. This phase closes that gap and builds the full inspection evidence chain.

1
Inspection & Estimation
Week 1–2
Critical Path
Photo evidence, structured estimate sending, customer approval tracking, hard gate before work begins, and portal-side approve/decline.
A
DB Migration
  • Create job_photos table — columns: id, job_id, org_id, photo_type (enum: inspection | post_service), storage_path, caption, uploaded_by, created_at
  • Add customer_approval fields to jobs: approval_status enum (pending | approved | declined), approved_by_channel enum (staff | portal | whatsapp), approved_at timestamp, approved_by_user UUID nullable, decline_reason text nullable
  • Create Supabase Storage bucket job-photos — private, signed URL access, RLS policy: users can only read photos from their own org
B
Photo Upload — Inspection
  • Add "Inspection Photos" card on job detail page — visible to technician, admin, and manager roles when job is in inspection or later status
  • Upload button with file picker (accept="image/*") — supports multiple selection; shows a thumbnail preview grid immediately after selection before upload
  • Storage path pattern: {org_id}/{job_id}/inspection/{uuid}.{ext}
  • After upload, photos displayed in a 3-column grid with an optional caption field per photo; captions stored in the job_photos table
  • Use Supabase Storage createSignedUrl (24h TTL) for display — never expose raw storage paths
C
Photo Upload — Post-Service
  • Same component pattern as inspection photos but photo_type = 'post_service'
  • Shown in a separate "Post-Service Photos" card on job detail — only editable when job status is in_service or ready
  • Storage path: {org_id}/{job_id}/post_service/{uuid}.{ext}
  • Read-only (display only) once job reaches delivered
D
Send Estimate Action
  • Add an explicit "Send Estimate to Customer" primary action button on the job detail page — shown only when: (1) job status is inspection, and (2) at least one part or labour line has been added
  • On click: transitions job to estimate_sent, sets approval_status = 'pending', fires a rich notification (not the generic template)
  • Rich message format: "Inspection complete for Job #JS-001. Estimate: Screen replacement (1 × ₹1,800) + Labour (₹400) = Total ₹2,200. Approve or view details: [tracking link]"
  • This button replaces the generic "→ Estimate Sent" status transition for this specific step — the generic transition button is hidden when rich send is available
  • Tracking portal link (/track/{portal_token}) is included in the message body
E
Customer Approval Tracking — Staff Side
  • New "Customer Approval" card on job detail — visible once status reaches estimate_sent
  • Shows current approval status with a coloured badge: Pending (amber), Approved (green), Declined (red) — plus the timestamp and channel when set
  • Staff action buttons: "Mark as Approved" and "Mark as Declined"
  • Declined flow: reveal a text field for decline reason → on confirm, approval_status = 'declined', job transitions back to inspection so technician can revise the estimate
  • Approved flow: sets approval_status = 'approved', approved_by_channel = 'staff', records the staff user ID and timestamp — the "→ In Service" button becomes active
F
Hard Gate — In Service Transition
  • Modify the transition_job_status Supabase RPC: if p_new_status = 'in_service', check approval_status = 'approved' — throw a descriptive error if not
  • On the job detail UI, disable the "→ In Service" transition button when approval is not yet recorded; show a tooltip on hover: "Customer approval required before work can begin"
  • The disabled state is visually distinct — greyed out with a lock icon — not just opacity
G
Customer Portal — Approve / Decline
  • On /track/[token], when job status = estimate_sent: show the full estimate breakdown (already rendered) plus two new action buttons — "Approve Repair" (green) and "Decline" (red/outline)
  • Approve: calls a new Supabase RPC approve_estimate_via_portal(p_token, p_decision, p_decline_reason) — validates the token, sets approval fields, sends a staff notification that the customer approved
  • Decline: shows an inline text input for reason → on confirm, submits with p_decision = 'declined' and the reason text
  • After either action: portal transitions to a confirmation screen — Approved shows a green confirmation + next steps; Declined shows an acknowledgement that the service center will be in touch
  • Buttons are hidden once a decision is recorded (idempotent)
H
Estimate Notification with Line-Item Breakdown
  • The "Send Estimate" action (D above) builds the message dynamically from the actual job_parts rows — not from the generic notification template
  • Format: each part as Item name (qty × ₹unit) = ₹line_total, then a separator line, then Total: ₹X
  • Portal tracking link is appended: Track & approve: https://…/track/{token}
  • Message is passed directly to the send-notification edge function via a custom_message override parameter (add this param to the edge function) — bypasses the template system for this specific trigger
  • Notification log records the rich message body as normal
Phase 2 · Week 3

Job Management Completeness

Fills in the missing operational pieces that front desk, technicians, and managers use every day — overdue visibility, smarter filters, structured notes, and the technician workload view.

2
Job Management Completeness
Week 3
Overdue flags, technician filtering, diagnosis notes, parts expected date, workload view, and outstanding balance warnings at intake.
A
Overdue Flag on Job List
  • On the jobs list page, any job where estimated_delivery < today AND status is not delivered gets a red "Overdue" badge rendered next to its status badge
  • Add an "Overdue" quick-filter chip at the top of the jobs list alongside existing status filters — clicking it filters to all overdue open jobs across all statuses
  • Dashboard "Overdue" stat card (already exists) becomes a link that navigates to /jobs?filter=overdue
  • Overdue logic: for jobs in parts status, compare against parts_expected_date (Phase 2D below) rather than estimated_delivery
B
Technician Filter on Job List
  • Add a "Technician" dropdown filter on the jobs list page — populated from users with roles technician and manager in the active branch
  • Selecting a technician adds assigned_tech_id to the Supabase query filter
  • "Unassigned" option to filter for jobs with no technician assigned — a common management view
  • Filter persists in the URL as a query param so it can be bookmarked or shared
C
Customer Name Search on Job List
  • Extend the current search box to match against both job_number and customers.full_name — currently only job_number is searched
  • Implementation: use a Supabase .or() filter with an inner join on the customers relation, or use a search_term computed column via a DB view
  • Also match against customers.phone — staff often search by phone at the counter
D
Awaiting Parts — Expected Arrival Date
  • Add column parts_expected_date (date, nullable) to the jobs table
  • When transitioning to parts status, the transition modal shows an additional date picker field: "Expected parts arrival date" (required for this specific transition)
  • On the job detail header area, when status = parts, show: "Parts expected: [date]" in amber — or "Parts overdue" in red if the date has passed
  • Overdue report (Phase 4A) uses this date instead of estimated_delivery when status is parts
E
Diagnosis Notes & Resolution Summary
  • Add two columns to jobs: diagnosis_notes text nullable, resolution_summary text nullable
  • On job detail, add a "Diagnosis" textarea — editable by technician/admin/manager when status is inspection or later; auto-saves on blur
  • Add "Resolution Summary" textarea — editable only when status is in_service, ready, or delivered
  • Both fields are visible to staff at all times; shown in the customer portal under a "Technician's Findings" section (only diagnosis when status ≥ estimate_sent; resolution when status ≥ ready)
F
Technician Workload View
  • New page at /technicians — accessible to admin and manager roles; linked from the sidebar under a "Team" section
  • Each technician shown as a card: avatar/initial, name, role, and a mini status breakdown — # jobs In Service, # Awaiting Parts, # total open
  • Cards sortable by open job count (most loaded first)
  • Clicking a technician card navigates to /jobs?tech={id} — the jobs list filtered to that person
  • Data is a single Supabase query grouping jobs by assigned_tech_id and status
G
Outstanding Balance Warning at Intake
  • On the new job form (Step 1 — Customer), when a repeat customer is detected by phone number, query their invoice history for any outstanding_balance > 0
  • If found, show a prominent amber warning banner below the customer match indicator: "⚠ This customer has an outstanding balance of ₹2,200 from Job #JS-2026-08-00098. Please collect before proceeding."
  • Warning is informational only — it does not block job creation (a manager may override) but is visually prominent so front desk cannot miss it
  • Show the job number as a link so staff can open the old job to collect payment in another tab
Phase 3 · Week 4

Customer Portal Enhancements

The portal is currently read-only beyond status tracking. This phase makes it interactive and complete — photos, invoice downloads, device history, and warranty tracking.

3
Customer Portal Enhancements
Week 4
Photos in portal, invoice PDF download, device job history, and warranty period tracking — making the self-service portal genuinely useful to customers.
A
Inspection & Post-Service Photos in Portal
  • Fetch job_photos rows via the get_job_by_portal_token RPC (extend it to include photos)
  • Inspection photos visible after status reaches estimate_sent — shows customer what the technician found
  • Post-service photos visible after status reaches ready — shows what was fixed
  • Display as a horizontal scrollable photo strip with tap-to-enlarge (lightbox overlay, no library needed — native <dialog>)
  • URLs are generated server-side as short-lived signed URLs (via edge function) so they never expire while the customer is viewing — refresh on token expiry
B
Invoice Download from Portal
  • When status is ready or delivered, show a "Download Invoice" button on the portal (only when an invoice record exists)
  • Implementation: Next.js API route GET /api/invoice/[token].pdf — validates the portal token, fetches the invoice + line items, generates a PDF and returns it with the correct content-type header
  • PDF generation: use a lightweight library (jsPDF or pdf-lib) server-side — no browser print dependency
  • Invoice PDF contents: org name, branch address & phone, customer name, job number, date, line-item table (description / qty / unit / total), grand total, payment mode & status, a "Thank you" footer with warranty reminder
  • Also accessible from the staff-side job detail — "Print Invoice" button using the same endpoint
C
Device History in Portal
  • Below the current job, show a "Past Jobs for This Device" section — all previous jobs for the same asset.primary_identifier
  • Fetched as part of the portal RPC — join assets → jobs filtered by same primary_identifier and not the current job
  • Read-only display: date, job number, status badge, issue category — no links (customer portal is stateless per token)
  • Hidden if no past jobs exist for the device
D
Warranty Period Tracking
  • Add column warranty_expires_at (timestamptz, nullable) to the jobs table
  • When a job transitions to delivered, automatically set warranty_expires_at = delivered_at + warranty_days — warranty days configurable per org in settings (default 30 days)
  • Customer portal: when status = delivered and within warranty window, show a green banner: "Warranty valid until [date]. Quote Job #JS-XXXX for any warranty service." — after expiry, show grey: "Warranty expired [date]."
  • Staff-side job detail: show warranty status in the header area once delivered; admin/manager can manually edit the expiry date
  • Add warranty days setting to org settings page (/settings/org)
Phase 4 · Week 5

Reports Expansion

Head office currently has no cross-branch visibility. The existing reports page is single-branch and missing overdue aging, margin breakdown, and export. This phase delivers everything needed for the head office dashboard.

4
Reports Expansion
Week 5
Overdue aging report, cross-branch revenue, parts cost vs margin, customer return rate, branch comparison table, and one-click CSV/PDF export.
A
Overdue Jobs Report
  • Dedicated "Overdue" tab in the reports page — list of all jobs past their expected date, sorted by aging (most overdue at the top)
  • Columns: Job #, Customer, Branch, Technician, Status, Expected Date, Days Overdue
  • Days Overdue is a computed column: today - expected_date — shown with a red badge for >3 days, amber for 1–3 days
  • Filterable by branch (admin sees all 7 branches; manager sees own branch only)
  • Parts-status jobs use parts_expected_date; all others use estimated_delivery
B
Revenue by Branch (Cross-Branch)
  • New "Branch Revenue" section in reports — admin-only (hidden for manager role)
  • Horizontal bar chart — one bar per branch, length proportional to revenue in the selected date range
  • Table below the chart with columns: Branch, # Jobs Completed, Revenue (₹), Avg Job Value (₹), # Currently Overdue
  • Sortable by any column; totals row at the bottom
C
Parts Cost vs Revenue (Margin)
  • The job_parts table already tracks unit cost per part — aggregate it by branch and period
  • Show: Revenue, Parts Cost, Labour Cost, Gross Margin (₹ and %) — per branch and overall
  • Simple table layout — no chart needed; margin % highlighted in green if >50%, amber if 30–50%, red if <30%
D
Customer Return Rate
  • Metric: (customers with 2+ jobs) ÷ (total customers with at least 1 job) × 100 = return rate %
  • Show as a headline stat card, plus per-branch breakdown
  • Table: Top 10 most frequent customers — name, phone, # jobs, total revenue from them
E
Branch Comparison Table
  • Admin-only view — side-by-side table with all branches as columns and metrics as rows
  • Metrics: Open Jobs, Completed (period), Revenue (period), Avg Turnaround Days, # Overdue, Technician Count
  • Cells with the best value in a row get a subtle green highlight; worst value gets a subtle red highlight
  • Scrollable horizontally on mobile
F
Export to CSV / PDF
  • CSV export: "Export CSV" button on every report table — builds the CSV string client-side from the already-fetched data, triggers a download via URL.createObjectURL(Blob). No server call needed.
  • PDF export: "Print / PDF" button triggers window.print() — add a @media print stylesheet that hides the topnav, sidebar, filter controls, and export buttons, leaving only the data tables formatted cleanly
  • CSV filename convention: servicedesk-{report_name}-{date}.csv
Phase 5 · Week 6

Branch & Settings Completeness

Operational configuration that branch managers and head office need. Most of this is UI wiring — the DB columns already exist or are small additions.

5
Branch & Settings Completeness
Week 6
Working hours, holiday schedule, job sheet prefix configuration, and the estimate breakdown notification toggle.
A
Working Hours per Branch
  • Add column working_hours JSONB to the branches table — stores an object keyed by day (mon–sun), each with open (bool), from (HH:MM), to (HH:MM)
  • On the branch settings page (/settings/branches), add a working hours configurator — 7 rows (Mon–Sun), each row has: toggle (open/closed), and if open: time-from and time-to selectors
  • Save to the branches table on confirm; display the current schedule as a read-only grid when not editing
  • Phase 1 scope: display only. Future: use in overdue calculations to exclude non-working hours
B
Holiday Schedule per Branch
  • Add column holidays JSONB array to branches — each item: { date: "YYYY-MM-DD", name: "Republic Day" }
  • On the branch settings page, add a "Holidays" section — shows a list of existing holidays with a delete button each, plus an "Add Holiday" form (date picker + name input)
  • Pre-populate with common Indian national holidays for the current year as a one-click import option
C
Branch-Specific Job Sheet Prefix
  • The job_prefix column already exists on the branches table — wire it to the branch settings UI
  • Show a text input on each branch's settings card: "Job Sheet Prefix" — e.g. KTH for Kothrud, PMP for Pimpri
  • Show a live preview below the input: KTH-2026-08-00001
  • Verify the DB trigger that generates job_number uses branches.job_prefix; fix if it falls back to a hardcoded string
  • Warn if prefix is changed after jobs already exist: "Changing this prefix will not rename existing job numbers — only future jobs will use the new prefix."
D
Notification Settings — Estimate Breakdown Toggle
  • In the notification settings page, add a toggle under the estimate_sent trigger row: "Include full line-item breakdown in estimate message" (on by default)
  • When ON: the "Send Estimate" action (Phase 1D) sends the rich per-item message
  • When OFF: falls back to the generic estimate_sent template — useful for orgs where message length is a concern (e.g. SMS character limits)
  • Store as notification_triggers.estimate_sent.rich_breakdown boolean in org_settings
Phase 6 · Week 7–8

Push Notifications & WhatsApp Webhook

The hardest phase — external integrations that require infrastructure setup beyond the app itself. Each deliverable is independently deployable.

6
Push Notifications & WhatsApp Webhook
Week 7–8
Browser push for technicians, WhatsApp reply parsing for customer approval, and automated time-in-service tracking.
A
Push Notifications for Technicians
  • Implement Web Push (PWA) for technician role — service worker is already registered (components/pwa/service-worker-register.tsx)
  • Generate VAPID key pair one-time — store VAPID_PUBLIC_KEY and VAPID_PRIVATE_KEY in environment variables
  • Add a push_subscriptions table: user_id, endpoint, p256dh, auth, created_at — one row per browser/device per user
  • On technician login: prompt for push permission and POST the subscription object to /api/push/subscribe
  • Trigger: new job assignment (assigned_tech_id set or changed) → Supabase DB webhook fires → send-push-notification edge function → finds the technician's subscriptions → sends Web Push to each
  • Push payload: job number, customer name, issue category — tapping the notification opens /jobs/{id}
B
WhatsApp Reply Webhook — Estimate Approval
  • Customer replies "YES", "APPROVE", "OK", or "HA" (Hindi affirmative) to the estimate WhatsApp message → auto-approves the estimate without any staff action
  • Webhook endpoint: POST /api/wa-webhook — validates the Twilio or 2Factor signature, parses the incoming message body and sender phone number
  • Lookup logic: find the most recent job for this phone number that has approval_status = 'pending' and status = estimate_sent
  • On match: call approve_estimate_via_portal RPC with approved_by_channel = 'whatsapp' — sends a confirmation WhatsApp back to the customer: "Your approval has been received for Job #JS-001. We'll start work shortly."
  • Decline keywords: "NO", "CANCEL", "DECLINE" → sets approval_status = 'declined' and transitions job back to inspection
  • Staff-side: when approval came via WhatsApp, the Approval card shows a "WhatsApp Reply" channel badge
  • Twilio setup: set the webhook URL in the Twilio console for the WhatsApp sender number; for 2Factor, configure the reply webhook in their dashboard
C
Estimated vs Actual Time Tracking
  • Add two columns to jobs: work_started_at (timestamptz), work_completed_at (timestamptz)
  • Set automatically in the transition_job_status RPC: work_started_at on transition to in_service; work_completed_at on transition to ready
  • Computed field: actual_hours = EXTRACT(EPOCH FROM (work_completed_at - work_started_at)) / 3600
  • Job detail page header: show "Time in service: 4h 23m" once both timestamps are set
  • Technician report (Phase 4): add "Avg Time in Service (hrs)" column per technician — roll up from all their completed jobs in the period
